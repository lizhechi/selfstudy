# AI Learning Project — Anchor v0.3

> 状态：Initial Anchor  
> 版本：v0.3  
> 性质：长期项目级锚点  
> 作用：定义本项目的长期目标、学习原则、能力边界、与 ProjectVox 的关系，以及后续规划文件的职责边界。  
> 本文件不承担具体课程表、单模块教学细节、每日任务或练习清单。

---

## 1. 项目定位

本项目是一个与 ProjectVox 并行推进的长期 AI 学习项目。

目标不是追逐某一代模型、某一种 AI 产品或某套短期流行工作流，而是系统建立能够跨模型、跨工具迁移的 AI 基础认知与工程能力，使学习者能够：

- 理解现代 AI / 大语言模型的基本工作方式与主要局限；
- 有能力高质量地使用、约束、评估和调度 AI；
- 理解并构建 Agent、RAG、工具调用、上下文系统、评测系统等现代 AI 应用组件；
- 将 AI 作为软件工程能力的一部分，而非黑箱式生产工具；
- 随模型能力持续增强，逐步从“AI 使用者”成长为“AI 系统设计者、评估者与 Agent 协调者”；
- 将这些能力长期反哺 ProjectVox 及其他真实项目。

本项目默认不以“成为基础模型研究员”作为主要培养目标。

## 2. 长期能力目标

本项目最终希望建立的不是“会使用几个 AI 工具”，而是一套完整、可迁移的能力结构。

### 2.1 模型理解

应逐步理解：

- token 与 tokenizer；
- context window；
- sampling 与生成行为；
- embedding；
- Transformer / attention 的核心思想；
- 推理模型与普通生成模型的差异；
- hallucination、上下文污染、指令冲突等失败模式；
- 模型能力、延迟、成本与可靠性之间的权衡；
- 模型训练、微调、推理的大致技术链路。

目标不是默认要求完成研究级数学推导，而是达到足够支撑工程判断的理解深度。

### 2.2 AI 任务设计

应能够把模糊目标转化为：

- 明确任务；
- 输入；
- 输出；
- 约束；
- 可验证条件；
- 失败条件；
- 评估标准。

Prompt 不应被视为“咒语优化”，而应被理解为人机任务接口设计的一部分。

### 2.3 Human–AI Communication / Task Specification

应系统掌握与 AI 高效沟通、传递复杂意图和组织任务上下文的能力。

重点包括：

- 将模糊想法转化为清晰目标；
- 区分事实、假设、担忧、决策与开放问题；
- 明确约束、优先级和不可修改项；
- 设计输出形式与验收标准；
- 判断什么时候应补充上下文，什么时候应删除无关信息；
- 将复杂问题压缩为高信息密度表达；
- 在探索性交流与执行性任务之间切换；
- 让模型明确表达不确定性，而不是强行给出确定答案；
- 在多轮交流中维护任务状态和讨论主线。

Prompt 不应被理解为“寻找神奇措辞”，而应被视为：

> **人类意图、上下文、约束与验收标准的接口设计。**

### 2.4 问题树与分支管理

复杂问题允许自然发散，不要求强行线性思考。

但应建立稳定的问题管理机制：

- 将问题组织为主问题、依赖问题、边界问题与延伸问题；
- 明确当前正在推进的主节点；
- 新出现的问题先判断是否阻塞当前结论；
- 阻塞当前结论的问题可以立即下钻；
- 不阻塞当前结论的问题进入待处理分支 / parking lot；
- 当前节点收敛后，再回收并处理已挂起分支；
- 定期重新确认原始目标是否已被偏离；
- 对大型问题允许先建立问题树，再逐层回答。

目标不是减少问题数量，而是：

> **在保留发散能力的同时，维持依赖关系、优先级和收敛能力。**

### 2.5 Agent 与工具系统

应逐步掌握：

- tool calling；
- 多步任务执行；
- Agent loop；
- 状态与记忆；
- 权限边界；
- sandbox；
- 失败恢复；
- 日志与可观测性；
- 单 Agent 与多 Agent 协作；
- 人类监督点；
- 自动化工作流。

### 2.6 Context Engineering

应理解并实践：

- 什么信息应该进入上下文；
- 什么信息不应长期占据上下文；
- 长期项目如何组织规范、状态、决策和执行信息；
- RAG 与直接上下文注入的区别；
- 信息检索、召回、排序和引用；
- 如何降低信息过载、陈旧信息和冲突规范带来的错误。

### 2.7 Evaluation

Evaluation 是本项目的核心能力之一。

应逐步掌握：

- 单元测试与自动验证；
- benchmark；
- regression testing；
- LLM-as-judge 的用途与风险；
- 人工评估；
- 数据集设计；
- failure taxonomy；
- 对 Agent 成功率、错误类型、成本和延迟进行系统评估；
- 区分“结果看起来不错”与“结果经过验证”。

### 2.8 AI Systems Engineering

应逐步建立：

- API 使用；
- structured output；
- RAG；
- embeddings；
- 向量检索；
- 本地模型与云模型；
- 推理服务基础；
- caching；
- latency / throughput / cost；
- observability；
- 权限隔离；
- 数据安全；
- 模型切换与供应商解耦；
- AI 功能在真实软件系统中的架构边界。

### 2.9 AI-Assisted Software Engineering

应能够安全、高效地让 AI 参与：

- 阅读代码库；
- 编写代码；
- 重构；
- 测试；
- 调试；
- benchmark；
- 文档维护；
- repository 操作；
- 原型探索；
- 多文件修改。

长期目标不是让 AI 替代对代码的理解，而是提高开发者能够可靠掌控的软件复杂度和规模。

## 3. 学习原则

### 3.1 理解优先于工具熟练度

不得把“会用某个产品”误认为掌握 AI。

工具和模型可以快速变化；本项目优先积累可跨工具迁移的概念、方法和判断力。

### 3.2 核心概念必须真正建立心智模型

第一次接触重要概念时，应通过解释、实验、代码、失败案例和实际观察建立理解。

不要求所有知识都从数学第一原理重新推导，但禁止长期停留在“知道名词、不会解释、无法判断什么时候使用”的状态。

### 3.3 允许发散，但必须能够回收

探索阶段允许一次出现大量相关问题，也允许在讨论主问题时继续产生新的分支。

不应为了表面整洁压制有价值的联想。

但复杂讨论必须逐步具备：

> 主问题 → 分支判断 → 必要下钻 → 非阻塞分支挂起 → 当前节点收敛 → 分支回收

的基本机制。

高质量 AI 沟通不要求一次只提出一个问题，而要求始终知道：

- 当前真正要解决什么；
- 哪些新问题会改变当前结论；
- 哪些问题可以稍后处理；
- 哪些分支已经解决；
- 哪些分支仍然开放。

### 3.4 实践必须伴随验证

任何 AI 系统的实现都不以“跑起来”作为完成标准。

应逐步建立：

> 假设 → 实现 → 测试 → 观察 → 评估 → 修正

的基本工作循环。

### 3.5 不把手工劳动当作学习目标

对于首次出现、具有基础性或关键架构意义的内容，应优先亲自实现和调试。

对于已经理解的重复性代码、脚手架、机械性工作、一次性实验等，可以主动使用 AI 加速。

判断学习质量的核心标准是：

- 能否解释；
- 能否修改；
- 能否调试；
- 能否验证；
- 能否发现明显错误；
- 能否重新设计。

而不是是否逐字符手写全部代码。

### 3.6 不追逐模型版本

不得因为某一代新模型发布而频繁推翻学习路线。

新模型和新工具应作为观察对象和实验材料。

只有当技术变化实质性改变长期能力结构时，才升级本 Anchor。

### 3.7 学习深度服从实际价值

AI 研究底层知识可以逐步深入，但不默认要求：

- 研究级 Transformer 数学；
- 大规模预训练；
- 分布式训练；
- CUDA kernel 研究；
- optimizer 研究；
- scaling law 研究。

若未来实际目标变化，再建立对应专项路线。

### 3.8 必须保留软件工程主线

AI 能力不能替代：

- 编程基础；
- 数据结构；
- 状态管理；
- 内存；
- 并发；
- 网络；
- 调试；
- 性能；
- 测试；
- 架构。

AI 越能大规模生成软件，开发者越需要具备判断和控制复杂系统的能力。

## 4. 与 ProjectVox 的关系

本项目与 ProjectVox 并行，但职责不同。

### ProjectVox

ProjectVox 是长期真实产品与软件工程主项目，承担：

- 游戏与平台实现；
- 体素系统；
- 软件架构；
- 性能；
- 工程实践；
- 长期作品积累。

### AI Learning Project

本项目承担：

- AI 基础认知；
- Agent 工程；
- Context Engineering；
- Evaluation；
- RAG / Retrieval；
- AI Systems Engineering；
- AI-assisted software engineering；
- AI-native project workflow。

### 双向关系

允许：

- 使用 ProjectVox 作为真实 AI 工程实验环境；
- 将成熟 AI 工作流迁移到 ProjectVox；
- 将 ProjectVox 中真实遇到的问题带回本项目研究；
- 使用 AI 项目中的成果改善 ProjectVox 的文档、测试、Agent 协作与开发流程。

禁止：

- 因 AI 学习项目不断扩张而长期阻塞 ProjectVox；
- 为了给 AI 项目找实验对象而污染 ProjectVox 正式架构；
- 把尚未验证的 AI 工作流直接升级为 ProjectVox 项目规范。

## 6. 教学方式

本项目默认采用：

> 概念理解 → 最小实验 → 亲自实现 → 使用 AI 辅助 → 评估 → 小项目 → 真实工程迁移

教学过程中应主动区分：

### 学习模式

适用于首次接触的核心知识。

特点：

- 节奏较慢；
- 强调解释；
- 学习者亲自写核心实现；
- 故意暴露部分错误并进行调试；
- 不急于让 Agent 全自动完成。

### 工程模式

适用于已经建立理解的内容。

特点：

- AI 可以生成较大比例代码；
- 学习者负责 review；
- 必须测试；
- 必须理解关键路径；
- 更关注系统质量而非手工输入量。

### 探索模式

适用于未知方案比较。

特点：

- 快速原型；
- 可大量使用 Agent；
- 允许一次性代码；
- 强调 benchmark 与结论；
- 不默认进入正式代码库。

## 7. 掌握判据

一个主题不以“课程看完”作为完成标准。

原则上应逐步达到以下能力中的多数：

- 能用自己的语言解释；
- 能识别适用场景；
- 能识别明显不适用场景；
- 能完成最小实现；
- 能阅读 AI 生成实现；
- 能修改实现；
- 能定位典型故障；
- 能设计测试；
- 能比较多个方案；
- 能说明主要 trade-off；
- 能将知识迁移到新问题。

## 8. 主动输出与作业体系

本项目不得以“听懂讲解”或“看完课程”作为主要学习方式。

教学必须持续包含学习者的主动输出，使理解能够转化为可验证的表达、判断、设计和实现能力。

### 8.1 核心原则

每个重要模块都应尽量包含以下循环：

> 理解 → 独立输出 → 反馈 → 修正 → 再输出 → 迁移

主动输出的目标不是增加形式负担，而是暴露：

- 概念理解中的空洞；
- 表达中的模糊与遗漏；
- 任务设计中的不可执行部分；
- 对 AI 输出缺乏审查能力的问题；
- “看起来懂”与“真正会用”之间的差距。

### 8.2 作业类型

教学中应按需要插入以下类型的作业：

#### 技术写作类

用于训练把复杂意图、约束和结论外化为清晰文本。

可包括：

- 任务说明；
- Prompt / Task Specification；
- 验收标准；
- 问题树；
- 模块说明；
- 短 ADR；
- 实验结论；
- 风险说明；
- 评测计划。

#### 改写类

给出低质量、模糊、冗余或结构混乱的输入，由学习者进行：

- 压缩；
- 重构；
- 补充约束；
- 明确目标；
- 增加验收标准；
- 区分事实、假设与开放问题。

#### 诊断类

给出失败的 AI / Agent 任务，要求判断主要问题来自：

- 上下文；
- 任务分解；
- Prompt / Specification；
- 工具权限；
- 模型能力；
- 数据质量；
- 评测设计；
- 系统架构；
- 人类监督不足。

#### 设计类

不给出唯一标准答案，由学习者独立设计：

- Agent workflow；
- RAG 方案；
- Evaluation pipeline；
- Context 组织方式；
- Tool use 流程；
- 权限与恢复机制；
- AI-native software workflow。

随后进行 critique、对比和修订。

#### 实现类

对重要基础机制，应安排最小可运行实现。

可包括：

- structured output；
- tool calling；
- 简单 Agent loop；
- RAG；
- embeddings / retrieval；
- evaluation script；
- logging / observability；
- 自动验证流程。

#### Review 类

应定期提供：

> 看起来合理、但存在隐藏问题的 AI 输出

由学习者进行：

- 代码审查；
- 方案审查；
- Prompt 审查；
- 架构审查；
- 评测审查；
- 风险识别。

目标是训练“发现 AI 错在哪里”，而不只是“让 AI 给答案”。

#### 解释类

学习者应定期脱离原始材料，用自己的语言解释：

- 一个概念是什么；
- 为什么成立；
- 什么时候适用；
- 什么时候不适用；
- 常见失败模式；
- 与相邻概念的区别。

必要时通过追问暴露理解漏洞。

#### 迁移类

完成核心模块后，应尽量把知识迁移到新的真实问题。

ProjectVox 可作为重要迁移环境，但不要求所有练习都直接进入其正式代码库。

### 8.3 阶段性闭卷输出

每完成一个较完整阶段，应安排新的、未直接练习过的场景进行独立输出。

闭卷输出的目的不是记忆考试，而是验证：

- 是否能在缺少模板的情况下重新组织知识；
- 是否能处理陌生约束；
- 是否能自行选择方法；
- 是否能设计可验证方案；
- 是否能识别不确定性；
- 是否真正形成可迁移能力。

阶段完成不得只依据“课程已看完”或“示例能够照着复现”。

### 8.4 建议性学习活动比例

作为方向性参考，而非机械硬约束，可大致保持：

- 约 40%：理解与讲解；
- 约 30%：独立输出；
- 约 20%：实验 / 编码；
- 约 10%：复盘与纠错。

具体比例应根据模块性质调整。

例如：

- 基础概念阶段可增加讲解；
- Agent / RAG 等工程模块可增加实验和实现；
- Human–AI Communication / Evaluation 可增加写作、审查和设计任务。

核心要求只有一个：

> **主动输出必须长期存在，不能被“AI 已经可以直接完成任务”所替代。**

## 9. 项目文件层级

本项目建议采用：

> Anchor → Learning Roadmap → Module Spec → Exercises / Mini Projects

### Anchor

定义长期目标、原则、边界和职责。

### Learning Roadmap

定义阶段顺序、依赖关系、阶段目标和大致学习深度。

### Module Spec

定义单个学习模块：

- 学习目标；
- 前置知识；
- 必须理解的概念；
- 必做实验；
- 完成判据。

### Exercises / Mini Projects

用于真实操作、编程、实验与评估。

Anchor 不应承担后三级文件的详细内容。

## 10. Anchor 升级规则

普通课程调整、模型更新、工具更新、单次实验结论不升级 Anchor。

仅当以下内容发生长期性变化时考虑升级：

- 项目最高层目标；
- AI 学习与 ProjectVox 的关系；
- 长期能力结构；
- 教学基本原则；
- 学习范围发生重大变化；
- 从 AI 工程方向转向基础模型研究等重大定位变化；
- 新技术范式使当前核心假设明显失效。

## 11. 当前长期方向

现阶段，本项目优先培养：

> AI Systems Engineering  
> + Agent Engineering  
> + Human–AI Communication / Task Specification  
> + Context Engineering  
> + Evaluation  
> + AI-Assisted Software Engineering

同时保留足够的大模型基础理论，使工程实践建立在真实理解上。

长期目标不是成为依赖某一代 AI 产品的高级用户。

长期目标是成为：

> **能够理解现代 AI 系统、设计可靠的人机协作流程、评估模型和 Agent、构建 AI 应用，并随着 AI 能力增强持续扩大自己可掌控系统规模的开发者。**
