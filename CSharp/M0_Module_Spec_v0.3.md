# M0 Module Spec：C# 开发环境、.NET 与程序结构 v0.3

> 文件名：`M0_Module_Spec_v0.3.md`  
> 所属项目：C# 面向对象程序设计学习项目。  
> 上位文件：`Anchor_v0.3.md`、`Roadmap_v0.3.md`。  
> 教材对应：入门篇第 1～2 章及微课 1～2；文件层级与现代模板差异作为必要补充。

## 1. 阶段目的、边界与前置诊断

M0 要解决的不是“记住一批名词”，而是建立第一条稳定工作链：知道自己正在使用什么工具，能从空白创建、运行和修改一个 C# 程序，能在 Visual Studio 中找到关键文件，并能依据错误信息做一次最小修复。

本阶段只建立后续所需的最小 .NET 心智模型，不深入类型系统、控制流、面向对象设计、垃圾回收算法、CLR 内部实现或编译器优化。变量、输入与输出只用于形成可运行证据，详细语义留到 M1。

前置诊断不作为淘汰门槛。开始时记录：

1. Visual Studio 2022 是否可以打开，是否安装“.NET 桌面开发”或可创建控制台项目的工作负载；
2. 新建项目时可见的模板名称、目标框架和“不要使用顶级语句”等选项；
3. 能否运行一个新建项目，以及运行结果出现在哪里；
4. 当前能否在“解决方案资源管理器”中找到解决方案、项目、`.cs` 与 `.csproj`；
5. 对“C#、.NET、Visual Studio、项目”四者关系的初始解释。

若环境暂时不可用，可以先完成结构辨认，但 M0 不得在没有真实运行证据的情况下判定完成。

## 3. 必学内容、关键辨析与推荐顺序

### 3.1 工具与运行链

首次接触时应能解释下列名称的全称、原义、中文含义和当前作用：

| 名称 | 最低限度理解 |
|---|---|
| IDE — Integrated Development Environment（集成开发环境） | Visual Studio 属于 IDE，用来编辑、组织、生成、运行和调试项目；它不是 C# 语言本身 |
| SDK — Software Development Kit（软件开发工具包） | 包含创建和生成应用所需的工具与参考组件；只安装运行时不等于拥有完整开发能力 |
| Runtime（运行时） | 提供执行已构建 .NET 应用所需的环境 |
| CLR — Common Language Runtime（公共语言运行时） | .NET 的托管执行环境，负责执行中间语言并提供内存管理等服务 |
| CIL — Common Intermediate Language（公共中间语言） | C# 源码通常先被编译成的中间表示；教材或工具中也可能见到 IL |
| JIT — Just-In-Time compilation（即时编译） | 程序运行期间把中间语言编译为当前机器可执行代码的常见机制 |

M0 使用的简化链路是：

`C# 源文件 → C# 编译器与生成系统 → 程序集中的中间语言 → CLR 执行（常见路径含 JIT）→ 运行结果`

预编译、AOT、ReadyToRun、垃圾回收细节和完整程序集元数据暂不展开。

### 3.2 解决方案与文件层级

- **解决方案（Solution）**：Visual Studio 用于组织一个或多个项目的工作区；当前工具链可能使用 `.sln` 或 `.slnx`。某些打开项目或文件夹的流程也可能没有独立解决方案文件，应记录实际情况，而不是把某一种扩展名当作唯一正确答案。
- **项目（Project）**：一次构建的配置与源文件集合；C# 项目的关键配置通常在 `.csproj`。
- **源文件**：以 `.cs` 为主，保存本人编写的 C# 代码。
- **`bin`**：通常保存生成后的可运行或可分发产物。
- **`obj`**：通常保存生成过程中的中间文件，不作为手工编写代码的位置。

必须能在 Visual Studio 的逻辑视图与 Windows 文件系统的实际目录之间建立对应，但不要求背诵所有自动生成文件。

### 3.3 程序结构与入口

教材重点展示显式结构：命名空间、类和 `Main` 方法。现代控制台模板也可能使用**顶级语句（top-level statements）**，让入口点不直接写成 `Main`。两者是不同表面形式，不代表程序没有入口。

本阶段需识别：

- `using` 指令、命名空间、类、方法、语句与注释各处于什么层级；
- `Main` 为什么是传统控制台程序的入口；
- 顶级语句如何隐藏样板结构；
- 大括号、圆括号、引号、分号与大小写如何影响编译；
- `Console.WriteLine` 与 `Console.ReadLine` 在最小程序中的输入输出作用。

### 3.4 错误类型与最小调试循环

- **编译错误**：程序未成功生成，优先读取错误列表中的文件、行号、错误代码与消息；
- **运行时错误**：程序已启动，但执行过程中失败；
- **逻辑错误**：程序可以运行，却得到错误结果。

M0 只要求稳定执行：复现问题 → 阅读信息 → 缩小位置 → 做一个最小修改 → 重新生成和运行 → 确认问题消失。

### 3.5 与 C++ 的边界

可迁移的是“程序有结构、语句有顺序、编译器会检查语法、入口负责启动”等抽象概念。不能直接照搬的是头文件与 `#include`、`std::cout`、项目生成方式、内存管理习惯，以及许多同名类型或访问机制的具体语义。

`using` 不是 C++ 的 `#include`；`.csproj` 也不是源代码文件。值类型 / 引用类型、属性、垃圾回收及更完整的对象差异将在后续阶段学习，本阶段只需避免把 C# 当作“换了关键字的 C++”。

推荐顺序：环境清点 → 创建并运行 → 对应文件层级 → 解释运行链 → 对照两种入口 → 错误修复 → C++ 边界复述。

## 4. 练习组

### 练习 A：项目结构寻路

创建一个控制台项目，分别在解决方案资源管理器和文件资源管理器中找到解决方案节点或实际解决方案文件（`.sln` / `.slnx`，若存在）、项目目录、主 `.cs` 文件与 `.csproj`。生成一次后再寻找 `bin` 与 `obj`。

提交一张带编号的截图或一份路径清单，并为每项写一句职责说明。不得只复制定义而不实际定位。

### 练习 B：两种入口与 C++ 迁移

读取一个顶级语句示例和一个显式 `class` + `Main` 示例：

1. 标出真正执行的语句与入口；
2. 说明两种写法在结构展示上的差异；
3. 把已有的 C++ “Hello World” 心智模型迁移到 C#，列出可复用和不可照搬的部分；
4. 亲自修改输出内容并运行，避免只做静态辨认。

### 练习 C：一次有证据的错误修复

在练习项目的副本或可恢复状态中引入一个简单编译错误，例如错误的大小写、缺失的引号或括号。先预测错误位置，再生成项目并记录完整错误信息；只修改一个最可能原因，然后重新生成和运行。

记录应包含：预期、实际现象、错误代码或关键消息、定位依据、修改和复验结果。不要同时制造多个错误。

## 5. Final Assignment：M0 最小开发链证明

从空白开始创建一个新的控制台项目 `CSharpM0Profile`。核心代码须由学习者亲自输入，并满足：

1. 程序显示项目名称和一句自定义说明；
2. 程序读取一次用户输入并把它以完整句子输出；
3. 项目关闭后能重新打开、生成并运行；
4. 提交项目关键路径清单，指出 `.sln` 或 `.slnx`（若所用流程创建）、`.csproj`、主 `.cs`、`bin` 与 `obj`；
5. 用自己的话画出或写出“源码到运行结果”的简化链路；
6. 附上练习 C 的错误修复记录，并说明一项与 C++ 相似之处和两项不能直接照搬之处。

允许查询教材、课堂材料与官方文档；是否掌握以实际创建、运行、定位和解释能力判断，而不是以闭卷记忆判断。

## 6. Final Review 与完成判据

| 审查项 | 通过表现 |
|---|---|
| 环境与运行 | 能在本人环境中独立打开、生成并重复运行 Final Assignment |
| 文件层级 | 能实际定位关键文件 / 目录，并正确区分解决方案、项目、源码与构建产物 |
| 程序结构 | 能指出所用模板属于顶级语句还是显式 `Main`，并解释入口与执行语句 |
| 运行链心智模型 | 能按正确方向说明 C#、编译、程序集 / 中间语言、CLR 与运行结果的关系；允许省略底层细节 |
| 调试证据 | 错误记录体现先读取信息、再做最小修改、最后复验，而不是只给修正后的代码 |
| 迁移边界 | 未把 `using`、项目文件或内存管理等机制直接等同于 C++ 对应物 |

完成 M0 需满足：Final Assignment 可运行；前四项无阻塞性误解；调试证据真实完整；C++ 边界至少达到判据要求。个别术语表述不够精确可以在 Review 中当场修正，但若仍不能独立运行或分不清项目、源码与构建产物，则暂不进入 M1。

## 7. 未通过时的最小补救路径

| 未通过类型 | 最小补救 |
|---|---|
| 无法创建或运行项目 | 只重做模板选择、工作负载检查和一次最小运行；保留报错截图，不提前学习语法 |
| 文件层级混淆 | 对同一个项目做“Visual Studio 节点 ↔ 磁盘路径”一一对应，不新建第二个项目 |
| 看不懂入口结构 | 并排标注顶级语句与显式 `Main`，只回答“从哪里开始、哪些语句会执行” |
| 术语关系混乱 | 用五张卡片重新排列 C#、Visual Studio、SDK、CLR、项目，并逐条纠正因果方向 |
| 只会照抄、不会修错 | 对已能运行的程序制造一个单一错误，强制按“信息—位置—修改—复验”完成一次闭环 |
| C++ 迁移过度 | 只针对发生混淆的两项做对照，不扩展成完整语言比较课 |

补救后只复查失败项及其直接依赖，不要求重做全部 M0。

## 8. Progress Snapshot / Completion Summary / Handoff 字段

如果 M0 在一个聊天中尚未完成而需要更换聊天，应生成或更新滚动文件 `M0_Progress_Snapshot_v0.1.md`。它只记录：

- 阶段编号与名称、Snapshot 最后更新时间；
- 所依据的 Anchor、Roadmap、当前 Module Spec 和 Startup Prompt 精确文件名；
- 已完成的诊断、练习和现有证据；
- 当前正在处理的任务及其未完成状态；
- 已确认的错误、薄弱点、环境信息与关键决定；
- 尚未回收的 Parking Lot；
- 下一聊天应执行的精确第一步；
- 若依据文件曾在阶段中途升级，记录新旧版本差异对现有证据与待办的影响及迁移结果。

该 Snapshot 不复制本 Spec，不预判 Final Review 结果，也不表示 M0 已完成。后续聊天读取它后跳过已有证据的部分，从记录的恢复点继续。

若 Snapshot 引用的依据文件不是当前版本，不得直接忽略旧状态或重做整个 M0。旧版可取得时先比较变化，保留仍符合当前判据的证据，只补做或复查受影响部分；旧版无法取得时以当前文件为准，只最小复查无法确认兼容的证据，不推测旧版内容。完成后更新同一 Snapshot 的依据文件、迁移说明与精确下一步。

M0 完成后保存 `M0_Completion_Summary_v0.1.md`，至少记录：

- 完成日期、Visual Studio 版本、项目模板与目标框架；
- Final Assignment 的位置或提交方式及运行证据；
- 已掌握项与仍需提示项；
- 本阶段遇到的错误、定位过程和最终修复；
- 仍易与 C++ 混淆的概念；
- Parking Lot 中尚未处理的问题；
- 对 M1“数据、表达式与控制流”的准备度结论；
- 若 Final Review 曾未通过，记录采用的最小补救路径及最终复查结果。

只有通过 Final Review 后才生成 Completion Summary；届时 Snapshot 不再作为当前阶段输入，其中具有长期价值的事实应收敛到 Completion Summary。
